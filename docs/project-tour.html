Start Here / 零基础

先别急着看代码：用 5 句话搞懂这个项目

你可以完全不懂动画、深度学习和 UE。把动作想成一段连环画，这个项目就是让 AI 根据前后文补画中间页。

约 30 分钟 · 不用一次读完
一句话比喻：AI 已经看到前 24 页（历史动作），也知道角色接下来往哪走（未来 Root 路线），还拿到 0–2 张未来关键页（硬参考）；它要补画剩下的未来页。
01 数据
先把动作变成标准格式

不同来源的动作，统一成 78 个关节、每秒约 120 帧、四个固定字段。就像把各种食材切成同样大小。

02 任务
不是凭空生成，是有条件补全

过去 24 帧已知，未来 24 帧角色往哪走已知，再加 0–2 帧未来姿势作硬参考；模型补其余未来帧。

03 模型
先读历史，再让未来帧互相商量

GRU 读历史动作，Transformer 让 24 个未来帧交换信息，最后输出每帧 78 个关节的姿态。

04 训练
用海量窗口反复做题

71,127 条动作切成约 249 万个训练窗口；验证集像模拟考，用来挑最好的权重，test 只做最后验收。

05 现状
离线能打，实时还没闭环

离线精度已经可用；UE 里的 AnimGraph、打包、多角色和脚滑补齐还没完成，不能对外说“运行时已搞定”。

02 / Experiment History

实验演进：主线不是一开始就长这样

这个项目最重要的资产不只是 3.09 M 参数的权重，而是“哪些路线被证伪、为什么被证伪、现在凭什么继续”。下面把失败路线、转折点和判断依据放在同一张时间线上，避免后来者重复踩坑。

复盘 · 后看
FAILURE → PIVOT → V3
人话这里记录“哪些路走不通、为什么”。第一次看可以只读每段时间线标题，不必啃完所有表格。
2026-09 / ROUTE A

VQ-VAE Token + 大主干

先把连续姿态压成离散码字，再让生成主干预测 token。结构看起来“更生成式”，实际把误差天花板压在了分词器上。

结论：已否证，不再作为主线
2026-09 → 2026-10 / ROUTE B

旧 79 骨 UE 闭环

30 fps、单输入窗口、VQ 重建、Root 由源动画驱动。它验证过线程与缓冲骨架，但与 78 骨 SOMA / 120 fps / 四输入契约不兼容。

结论：插件移除，只保留经验
2026-10 → 2026-11 / ROUTE C

直接回归姿态

跳过离散 token，直接从历史、未来 Root 和稀疏硬参考回归 24×702。任务变成“补间”，误差不再被码本封顶。

结论：当前主线，v3 封盘
2026-11-14 / POST-FREEZE

复现与口径复核

后续全量复现暴露接触损失 fps 写死 30 的缺陷；同时证明 20→30 epoch 只多换 0.08–0.19 cm，继续堆 epoch 不划算。

结论：保留 v3 主成绩，补充口径更正

归一化口径缺陷被定位

2026-10

训练侧使用落盘前已标准化的特征，评测侧却喂原始特征，`is_normalized` 又被写死为默认值。后果是训练目标与评测目标不是同一个量：30,000 步后关节误差从 108 cm 断崖到 310 cm。对齐口径后，同一评测下 RMSE 从 94.54 cm 降到 83.85 cm（−11.3%）。这是项目至今最大的单点收益，且不来自任何损失项。

接触损失 fps 缺陷与全量复现

2026-11-14

复核发现旧实现把脚速换算帧率写死为 30，而契约是 120.0048 fps；脚速进入平方后，`contact_weight=0.4` 实际只生效 1/16，等效 0.025。修复后用同强度对照验证“修复本身中性”；再测 0.1 与 0.4，前者四档 RMSE 涨 22–36%、脚滑只降 5–11%，后者直接发散。结论：不要再靠调 contact_weight 压脚滑。

Postmortem

失败路线总表：症状、根因与留下的资产

路线 / 改动观察到的症状根因证据留下的结论
VQ-VAE tokenizer + 大主干 码本约 20k 步后塌缩；每批 token 量化到同一码字；关节 RMSE 早期约 96.5 cm，训练到 100k 步仍约 84–86 cm。 码字里没有可优化信息，分词器退化；生成主干再大也无法突破 tokenizer 的重建天花板。 model/MotionWeaver/tokenizer/__init__.py、docs/refpose-v3-training-evaluation.md §11、paper/main.html §9/§11 离散 token 不是本任务的必要条件；姿态精度应直接优化。
旧 79 骨 UE 插件 能加载、能预览、能验证线程，但无法承接 78 骨 SOMA、120 fps、四输入 refpose。 契约代际不兼容：单输入 vs 四输入、79 vs 78 骨、30 vs 120 fps、VQ 重建 vs 条件生成。 docs/repository-layout.md、docs/refpose-ue-runtime-integration-research.md 旧会话层不能复用；线程、PoseBuffer、验收统计骨架可以沿用。
训练/评测归一化不一致 训练 loss 正常，评测 RMSE 断崖式恶化；30k 步后 108 → 310 cm。 一侧标准化、一侧原始特征，`is_normalized` 默认值掩盖了差异。 README.md “最近的实测结论”、paper/main.html §9 口径修复带来 −11.3%，比任何损失项都大；先对齐数据再调模型。
分片存储（2,000 窗口/片） 随机读取比整条 NPZ 还慢约 100 倍。 np.savez 打包后必须解压整包，随机访问代价极高。 docs/refpose-v3-training-evaluation.md §11 训练窗口存储应按字段、可 mmap，不按“片”打包。
tiny：每 clip 只存前 48 帧 读取很快，但大量窗口取到错误动作。 窗口 start 分布为 0–16,416，97.1% 的窗口不是从第 0 帧开始。 data/runtime/refpose_windows.py 注释、v3 记录 §11 正确性优先于缓存技巧；不能把“前 48 帧”当成整条动作。
LRU 从 256 加到 4096 期望减少 IO，实际更慢。 内存压力导致换页，LRU 命中收益被系统换页吞掉。 v3 记录 §11 缓存容量要跟内存预算一起评估，不是越大越好。
contact_weight 直接加到 1.0 脚滑改善，但位置精度退化约 40%。 接触项与位置项的量级关系决定了“用精度换脚滑”的交换比很差。 docs/experiments/2026-11-14-refpose-contact-fps.md 0.4 是旧口径的平衡点；修复 fps 后 0.4 会发散，不能照搬。
把验收指标直接写进损失 17 组同步数对照，关节位置损失效应 +0.10 cm，小于换种子的 0.56 cm 抖动；符号检验 p=0.75。 码本已塌缩，token 中没有可优化信息；损失项无法创造信息。 README.md、paper/main.html §9 先修表示与数据，再谈损失工程。
不要把“失败”理解成“没产出”。 这些实验留下了三类资产：可复用的工程骨架（线程、PoseBuffer、导出、测试）、可量化的否证（码本塌缩、fps 缺陷、存储反模式）、以及一套更严格的实验口径。后者决定了 v3 的数字是否可信。
ROUTE A / 已否证

VQ token 生成路线

  • 表示：连续姿态 → 离散码字 → token 序列。
  • 模型：VQ-VAE tokenizer + Root/Pose 大主干，结构复杂、显存与调参成本高。
  • 监督：重建 + token 预测；误差先经过量化，再进入生成。
  • 结果：码本塌缩到 perplexity=1.000；重建 RMSE 长期停在几十厘米级。
  • 根因：分词器退化后，生成主干没有可用的离散信息；这不是“再训久一点”能解决的。
  • 仍然保留：上游 G1 演示、历史对照、Tokenizer 代码与部分工程经验。
ROUTE C / 当前主线

RefPose 直接回归路线

  • 表示：78 骨 × (3 位置 + 6D 旋转)，直接输出 24×702。
  • 模型：GRU 历史编码 + 条件投影 + 3 层 Transformer，3.09 M 参数。
  • 条件：24 帧历史、24 帧未来 Root、0–2 帧硬参考；mask 末帧硬覆盖。
  • 结果：test 四档 5.28 / 3.22 / 3.22 / 2.17 cm；优于 Lerp 1.69–3.15 倍。
  • 代价：脚滑 6.9–8.7×，需 UE 端 IK/Foot Locking；Root 仍是 oracle。
  • 为什么继续：任务定义清晰、误差可分解、可导出 ONNX、可逐层验收。
Why It Failed

码本塌缩的判别

不是看 loss 是否下降，而是看 perplexity 是否长期接近 1、不同样本是否量化到同一码字、以及重建是否退化为自编码。只要这三件事同时出现，继续加 backbone 或调损失都没有意义。

Why It Works

直接回归的收益

误差直接落在关节位置与旋转上，没有量化瓶颈；参考帧用 torch.where 精确覆盖；训练与评测共享同一套归一化、窗口和 6D 排布。模型小，但每个设计都能被单独验证。

What Changed

真正的转折点

不是“换了个更大的模型”，而是把任务从“重建已知动作”改成“在稀疏参考下补全未来”，并把数据、归一化、窗口、6D、Root 权威逐项钉成契约。模型只是契约上的一个可替换部件。

如果只记三句话：① VQ token 路线的失败是表示层失败，不是训练时间不够；② 归一化口径修复比任何损失项都值钱；③ 当前 v3 的强项是离线姿态精度，不是 UE 运行时、脚滑或 Root 预测。把这三件事分开说，才不会把实验结果讲错。

Hold

Critical Detail

6D 旋转不是“按列拼接”

仓库里的 6D 是 row-major interleaved：每骨 6 个数按 m00,m01,m10,m11,m20,m21 排列。正确解码：

col0 = [0, 2, 4]
col1 = [1, 3, 5]
col2 = cross(col0, col1)
用错排布时，col2 会退化成近零向量，严重时除零得到 NaN。Root、部分手部叶骨最容易先崩。以 benchmark/manifest/refpose_manifest_v1.json 为准。
LEGACY / 已否证

VQ-VAE tokenizer + 大主干：为什么不走这条线

早期路线用 VQ-VAE 把动作离散成 token，再让主干生成 token。问题不是“训练不够久”，而是码本在 20k 步后塌缩到 perplexity=1.000， 每批所有 token 量化到同一码字，分词器退化为自编码器；关节 RMSE 卡在约 96.5 cm。 主线因此改为直接回归姿态。VQ 代码仍保留在 model/MotionWeaver/tokenizer/ 和 G1 参考演示中，但不再作为主线。

Loss

训练目标：精度优先，脚滑作为约束

total = 10 × position_loss
    + rotation_loss
    + 2 × velocity_loss
    + contact_weight × contact_loss
position / rotation

只在 visible = 1 - mask 的帧上计算；位置误差乘 pose_std 回到厘米量级，旋转用 6D 差平方。

velocity

预测与目标的帧间位移差，约束运动连续性，避免“每帧都对、连起来抽搐”。

contact

只惩罚“相邻两帧都接触、脚却还在滑”的帧对；脚速 = 世界坐标帧间位移 × 契约 fps。fps 必须取契约值，不能写死 30。

08 / Metrics & Contracts

指标不是一张表：先把口径、字段和数学关系钉死

同一个 5.28 cm，可能是“每 clip 等权、非锚点、oracle Root、test split”的结果，也可能是“全体关节平均、包含参考帧、不同契约”的结果。下面把可复算所需的字段、公式和不可比边界一次列清。

口径 · 查阅
CONTRACT → METRIC
人话这一章解释分数怎么算。先记住 RMSE 越小越好，而且只有同一套契约下的数字才能直接比。
Primary Metric

非锚点位置 RMSE

只统计模型真正生成的未来帧；参考帧由 mask 排除。先对每条 clip 求 RMSE，再对所有 clip 等权平均，避免长动作或窗口多的 clip 主导。

visible = 1 − mask
rmse_clip = sqrt( mean( (p_pred − p_gt)² × visible ) )
metric = mean_over_clips( rmse_clip ) × 100 # cm

位置误差在归一化域计算，乘 pose_std 回到米制；旋转是 6D 差平方，不参与主 RMSE 排名。主表单位统一为 cm。

Foot Slip

脚滑倍数：两个口径必须分开

只在“相邻两帧都接触”的帧对上统计。脚速 = 世界坐标帧间位移 × 契约 fps。倍数 = 生成脚速 ÷ 源动作同期脚速；源动作基准在 v3 记录中为 0.0261 m/s。

pair_t = contact[t] × contact[t−1]
speed_t = || world_foot[t] − world_foot[t−1] || × fps
ratio = Σ(speed_pred × pair) / Σ(speed_gt × pair)
# pooled：先合后除；逐 clip 均值：先求比再等权

pooled 与 逐 clip 均值 可差 50% 以上。引用时必须写清口径；不同源动作分母（0.0261 vs 0.0311）之间也不可直接比较。

Window Math

窗口切片与 anchor

start = row["start"]
middle = start + 24
end = start + 48
origin = root[middle − 1]
history_root = root_local(root[start:middle], origin)
future_root = root_local(root[middle:end], origin)
  • 历史 24 帧与未来 24 帧都相对“最后一帧历史 Root”表达，避免世界绝对位置泄漏。
  • origin 必须是 root[middle−1]；写成 root[middle] 会让整条 root_plan 偏一帧。
  • 窗口起点按 24 帧步长推进；窗口之间可以共享历史，但监督目标不重叠到参考泄漏。
  • k[:,1] 恒为 0，垂直高度保留在身体姿态中；Root 只承担水平位移与朝向。
Root Authority

Root 的权威与 p[:,0]

world = R(k) · p + k_pos
p[:,0] = −R(k)ᵀ · k_pos
回代误差由 float32 dtype 决定，实测 ≤ 1.1e−06
  • k.npy 是 Root 唯一权威；p[:,0] 不是第二条轨迹，而是它的逆变换。
  • 之前判“方向相反、无法对齐”，是比较首尾位移差时被两帧之间的旋转带偏，属于比较量选错。
  • UE 侧应直接读 k，不要试图从 p[:,0] 再推一条轨迹。
6D Rotation

最容易写错的一处：row-major 交织

正确排布
v = [m00, m01, m10, m11, m20, m21]

col0 = [v0, v2, v4]
col1 = [v1, v3, v5]
col2 = cross(col0, col1)

按正确排布解码时，78 根骨的 |col0 × col1| 都约等于 1.0；200 条随机 clip 最小值 0.999999693。

错误排布

仓库自带的 matrix_to_cont6d 是“按列拼接”，与本数据不兼容。误用后 Root、LeftHandRingEnd、RightHandIndexEnd、RightHandRingEnd 的叉乘模长会正好为 0，直接除零得到 NaN；另有 19 根骨落在 1e-2 以下。

不要用单列范数判断退化；真正的判据是 |col0 × col1|，因为 col2 由叉乘得到。

Regression Guards

最值得记住的五个反向测试

6D 误读

把交织排布换成按列拼接，反解必须不正交、gram 偏差 >1e−2；测试如期变红。

mask 软化

把 mask 当权重或做 lerp，导出后硬覆盖不再精确；测试必须抓到。

四输入失效

逐个扰动 history / root_plan / reference / mask，输出必须变化；否则图里丢了输入。

续训回弹

epochs 拉长后直接 load 旧 scheduler 会把 T_max 覆盖回去，LR 折返；测试要求重建日程。

窗口取错

tiny 只存前 48 帧时，97.1% 窗口会错；窗口 start 与文件内容必须对账。

产物半成品

ONNX 缺失不能 skip；hash 与 manifest 必须对得上。

Q1：为什么 doctor 过了，测试还是大量 skip？

doctor 检查解释器、依赖与基础环境，不保证大权重、训练视图和 UE Content 存在。这个仓库刻意把大数据留在 Git 外，所以缺数据时测试 skip 是预期行为。

真正要区分的是“缺输入”与“缺产物”：缺 manifest/权重可以 skip；缺导出的 model.onnx / onnx_manifest.json 必须 fail，否则半成品会被静默放过。

Q2：为什么不能重算 pose_mean / pose_std？

统计量绑定训练分区、骨架与数据版本，训练和推理都依赖同一组值。用全库或当前样本重算会改变输入分布，且这种漂移不会立刻报错。

实测用 3 条 clip 反推，与契约统计量最大差可达 43.02 cm（均值）/ 146.83 cm（标准差）；换 3 条 clip 又得到 34.12 / 100.00 cm。这是“重算会坏”的证据，不是全库上界。正确做法是重新构建 release，并让 manifest/hash 一起更新。

Q3：6D 旋转为什么会得到 NaN？

本仓库数据是 row-major 交织：m00,m01,m10,m11,m20,m21。正确解码是 col0=(v0,v2,v4)、col1=(v1,v3,v5)、col2=cross(col0,col1)。

如果按“前三个为第一列、后三个为第二列”的列拼接方式解码，某些骨的 |col0×col1| 会正好为 0，col2 除零后得到 NaN。先跑 tests/test_manifest_rebuild.py 的 6D 反向测试，不要靠肉眼猜。

Q4：raw_file 和 mmap_file 到底有什么区别？

raw_file 指向四键 NPZ；mmap_file 是逐字段 p.npy / r.npy / k.npy 的目录。旧契约可能只有 raw_file 且恰好写成目录名，所以代码保留回落，但新契约是两个独立字段。

全量 71k 的 clips 顺序与 mmap 目录命名顺序不一致；用 clip_index 代替 mmap_file 会读到别的 clip。这个坑在 MotionWindows._ensure_loaded 里有明确注释。

Q5：为什么接触损失里的 fps 错 4 倍，结果会差 16 倍？

脚速 = 帧间位移 × fps，进入 contact loss 后又平方，所以缩放是 (fps_true / fps_used)²。120.0048 / 30 ≈ 4，平方就是 16。

旧实现写死 30，导致日志里的 contact_weight=0.4 实际等效 0.025。修复后必须用契约 fps；测试 test_contact_loss_scales_with_contract_fps_squared 已锁定该关系。

Q6：续训为什么不能只 load model？

只恢复权重会让 AdamW 一阶/二阶动量、学习率、scheduler 进度、epoch/step、best/history 全部重新开始，训练会先“退一步”再爬。完整续训要恢复优化器、调度器、进度与历史。

把 20 epoch 拉到 30 epoch 时，不能直接 load 旧 scheduler：它会把 T_max 覆盖回旧值，余弦折返、LR 回升。正确做法是按“同一进度位置”重建日程，例如 20ep 的 155,620 步在 30ep 的新余弦上对应 7.50e-05。测试 test_larger_t_max_rebuilds_schedule_instead_of_rebounding 守着这一点。

Q7：训练进程为什么会在 Agent 调用结束后消失？

用 nohup 或普通后台命令挂在 Agent 的 bash 调用下，调用结束 systemd 可能停掉对应 scope，训练收到 SIGTERM。另一种情况是 OOM killer 命中 harness，连带杀掉同一 scope 的训练。

长任务用 tools/run_detached.sh 跑成独立 user unit，设置 MemoryHigh/MemoryMax/MemorySwapMax 和 OOMScoreAdjust，再用 systemctl --user status / 日志观察。具体流程见 .agents/skills/run-detached-jobs/SKILL.md。

Q8：ONNX 导出成功，为什么还不能说 UE 能跑？

阶段 1 只证明同一输入下 PyTorch 与 ONNX Runtime CPU 数值一致，以及 mask 硬覆盖仍在。它不证明 DirectML、UE 自带 ORT、打包、Shipping、多角色或动画线程预算。

UE 里用的是引擎自带的 ORT 1.24.1 + DirectML 1.15.4，与 pip 的 onnxruntime-directml 是两套运行时。必须在 UE 内重新做数值校验与 profiling，并确认 GRU 没有回退 CPU。

Q9：脚滑 6.9× 是不是说明模型完全不能用？

不能这样下结论。模型位置精度优于 Lerp 1.69–3.15 倍，脚滑从 17–22× 降到 6.9–8.7×，但确实未达 <5× 目标。剩余问题更像 Root 轨迹与步幅不匹配，以及位置/旋转通道不严格 FK 一致。

正确表述是“离线姿态精度达标，脚滑未达标，需 UE 端 IK/Foot Locking/步幅匹配补齐，尚未实机验证”。不能写成“已经解决脚滑”，也不能因为脚滑就否定整个姿态模型。

Q10：为什么同一个 5.28 cm，别人的报告对不上？

先核对六件事：contract hash、split、选窗策略（是否每 clip 中心窗口）、是否 oracle Root、是否只算非锚点帧、每 clip 等权还是全体平均。任何一项不同，数字都不可直接比。

再核对脚滑口径：pooled 还是逐 clip 均值、源动作分母是多少。v3 的 0.0261 m/s 与 full_release_v2 的 0.0311 m/s 相差 19%，直接比会得到错误结论。

Glossary

术语表

窗口 / window
48 帧：24 历史 + 24 未来；窗口起点按 24 帧步长推进。
锚点 / anchor
被 mask 选中的未来帧，作为硬参考；输出精确覆盖。
oracle Root
未来 Root 轨迹直接取自源动作；离线理想条件，不是控制器预测。
四键 NPZ
positions / rotations / timestamps / root_track。
契约 / contract
窗口、骨骼、fps、划分、统计量与哈希的冻结描述。
release
contract + windows + stats 的发布目录。
mmap
逐字段 .npy 内存映射，按页读取，不整包解压。
非锚点 RMSE
只统计模型真正生成的帧，排除硬参考帧。
脚滑倍数
生成接触期脚速 ÷ 源动作接触期脚速。
每 clip 等权
先算每条 clip 的均值，再对 clip 均值求平均，避免长动作主导。
6D 旋转
用旋转矩阵前两列表示旋转；本仓库是 row-major interleaved。
DML
DirectML；UE 内的 ORT 执行后端，当前尚未验证。
Pitfalls

十个容易踩的坑

01
统计量不能重算

mean/std 绑定 train 分区与权重；重算会悄悄改变输入分布。

02
6D 排布不能猜

以 manifest 为准；按列拼接会导致 col2 近零甚至 NaN。

03
fps 不能写死 30

主库是 120.0048 fps；接触损失里 fps 进平方，错了会放大/缩小 16 倍。

04
raw_file 与 mmap_file 不能混

前者是 NPZ，后者是 mmap 目录；写反会让评测/推理读不到数据。

05
不要只存前 48 帧

窗口起点分布很广，tiny 方案会让 97.1% 的窗口取错数据。

06
不要跨契约比数字

窗口步长、划分、来源版本不同，数字不可直接比。

07
VQ 路线已否证

码本塌缩到 perplexity=1.000；不要因为“结构更大”就回到主线。

08
Root 是离线代理

不是 CMC/Mover 的实际轨迹，也不是已观测 Actor Root。

09
UE 未闭环

没有 AnimGraph、打包、多角色、网络和实机验收，不要对外宣称运行时能力。

10
.build 不要整目录删

混有可重建产物和历史证据；按文件判断，先核对用途。
